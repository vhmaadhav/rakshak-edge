# Close three PS3 gaps before polishing the explainer

Rakshak Edge is a credible offline prototype on the Raspberry Pi 5, with measured latency, memory and energy, a deterministic verifier and a template fallback that guarantees safe output. It covers only part of Problem Statement 3 as the official text now reads. The network-traffic intrusion path is not wired into the service, the team's own SMS student flags **41.6% (471/1,133)** of legitimate Indian financial SMS, and the technical report and demo video do not exist yet. With 17 days to the **23 November 2026** Phase 1 deadline, the highest-scoring moves are to ship the required deliverables, wire in the existing network-IDS student with an honest cross-dataset evaluation, and fix or openly disclose the false-positive problem with an independent test set. Explainer faithfulness and Hinglish matter, but they sit behind those three. Phase 2 (PoC deadline **5 February 2027**, 74 days after Phase 1) can then take on the heavier model work: encoder distillation for Hinglish, a full adversarial matrix and possibly a Hindi-capable explainer. The organisers have not published judging weights, so the ranking below follows the seven judging aspects the first-edition FAQ lists as a proxy ([Arm 2026-27 page](https://arm-education.github.io/Arm-Developer-Labs/Bharat_AI_SoC_2026_27.html)).

## Where we stand against PS3 and the judging aspects

The PS3 text on the Arm page asks for a system that "classifies network traffic for intrusions, detects phishing URLs and scam SMS, explains threats in plain language, and recommends remediation, all without cloud dependence" ([Arm 2026-27 page](https://arm-education.github.io/Arm-Developer-Labs/Bharat_AI_SoC_2026_27.html)). The team's notes were read through an extraction model, so this wording must be checked against the live page before the report quotes it. Against that text, the components stand as follows.

Against the seven judging aspects, the picture is uneven. **Technical correctness** is the strongest area, because the pipeline is measured end to end, but its in-sample numbers are not labelled as in-sample. **Performance and optimisation** has real numbers (Llama load 7.5-11 s, decode 9.8-11.6 tok/s, RSS 1.84 GB, request p50/p95 about 1.7/3.0 s), but they rest on **40 rows** and an energy figure that is a PMIC estimate, not a calibrated measurement. **Documentation** and **demo and presentation** are missing outright. **Problem understanding** is weakened by the network-traffic gap. **Use of Arm tools** is compliant (ExecuTorch, Arm Cortex-A76), but the KleidiAI gains Arm reports apply to Armv9 with i8mm, and the Cortex-A76 has no i8mm, so the team should not claim KleidiAI speedups on the Pi ([Arm Community](https://developer.arm.com/community/arm-community-blogs/b/ai-blog/posts/llm-inference-llama-quantized-models-executorch-kleidiai)). **Novelty** rests on the deterministic verifier with a guaranteed-safe fallback, which is a real differentiator. The two-stage classifier-then-LLM shape resembles the Google DeepMind and Singapore GovTech on-device scam detector, which published no metrics, so the team's measured numbers are where it can stand out ([DeepMind blog](https://deepmind.google/blog/on-device-ai-scam-detection-mddi/)).

Three items deserve more explanation. On the false positives (rank 3), the notes show that the rules layer alone flags 1.06% of the same legit set, while the student flags 41.6%, so the student is the cause. The best-known fix in the notes is a two-stage design: an allowlist of DLT-registered transactional (T-type) templates and known bank senders, with scam-indicator rules (links, OTP-request phrasing, mismatched sender) that override the allowlist, and the student used only in a high-threshold band. The threshold must be set on a held-out legit set, not on the GroundLM set, because that set was used for rule design. Retraining needs group-aware splits by template cluster, two-judge label cleanup with kappa reported, and **minimal-pair** hard negatives (a legit template and the same template with a scam edit). The notes record that a plain hard-negative augmentation arm already failed, with FPR still 7-37%, so augmentation alone should not be repeated ([detector notes](https://zenodo.org/records/20480151)). On the day one question, the demo should stop presenting the quiet mode as clean detection. Both numbers belong on the slide: a 0.18% visible-warning FPR that comes with 23% visible recall.

On the network-IDS path (rank 2), the honest evaluation is the point. The notes show within-dataset F1 of 0.80-0.997 and no cross-dataset generalisation. The report should show the leave-one-dataset-out matrix and say plainly that the model does not transfer. A judge who sees the drop trusts the detector more than one who sees a single high number. The research note on adversarial robustness supports a family-by-family matrix in the same spirit ([arXiv 2609.01171](https://arxiv.org/abs/2609.01171)).

On the explainer (rank 5), the team already has the decisive safety property: the final output always passes because the template fallback catches every failure. The score question is therefore the **share** of the output that the LLM produces and its quality. The notes give two candidate fixes. The cheap one is the stop-rule change (sentence end, quotes ignored in-sentence, one retry), estimated at 0.3-0.7 s extra per sentence on average, mostly on failures. The heavier one is constrained decoding. ExecuTorch's grammar-constrained decoding (issue 19476) is open with no shipped path, so the practical route is a custom LogitProcessor in the C++ runner ([ExecuTorch #19476](https://github.com/pytorch/executorch/issues/19476)). Re-exporting the adapter to match Meta's QAT recipe (4-bit groupwise weights at group size 32, dynamic 8-bit activations, BF16 LoRA) is the likely cause of the retention gap (FP16 pass 97%, 8da4w 84%), but the notes give only partial recovery as the expectation. That makes it a Phase 2 item unless it turns out to be cheap ([TorchAO QAT](https://pytorch.org/blog/quantization-aware-training-in-torchao-ii/)).

Two lower-ranked items are worth a sentence each. Decode on the Pi is memory-bandwidth-bound. At 13.8 GB/s over roughly 1.1 GB read per token, the ceiling is about 12 tok/s, and the measured 9.8-11.6 tok/s is already 80-95% of it ([Arm Learn roofline](https://learn.arm.com/learning-paths/cross-platform/llm-decode-roofline/how-decode-uses-memory/)). Thread tuning will move prefill, not decode, so the team should spend little time on kernel tweaks and should cut generated tokens instead. The Llama 3.2 3B model would roughly halve decode speed and push RSS well beyond 1.84 GB on a 4 GB board with no cooler, so it stays out of the plan.

For Phase 2, the shortlist is announced in mid-December, which leaves about seven weeks to 5 February. The priorities are: a two-teacher distillation (mmBERT as one teacher, with a Hinglish-specific MuRIL or HingBERT as the second) using teacher-labelled transliterated and code-mixed data plus hard negatives from bank, UPI and OTP templates, checked against both the independent set and an adversarial matrix ([mmBERT](https://arxiv.org/html/2509.06888v1); [MuRIL](https://arxiv.org/abs/2103.10730v2)). The adversarial suite should be organised by perturbation family, with a pre-registered list that includes at least one encoding-level family and one family verified to survive SMS or RCS delivery. The Johnny-preprint finding that robustness transfers within a family but not across encoding attacks is the reason for this design ([arXiv 2609.01171](https://arxiv.org/abs/2609.01171)). The Android path can follow only if the organisers supply hardware or the team wants a second platform. The notes show that ExecuTorch Llama on phones has a single vendor-reported data point of about 50 tok/s, that Play policy restricts READ_SMS to default SMS handlers, and that a share-intent flow is the policy-safe entry point ([Google Play policy](https://support.google.com/googleplay/android-developer/answer/9047303)). Any Android work should start from a fixed LlmModule API read from source, which the notes did not confirm.

## Risks and items to verify

The notes contain conflicting or unverifiable figures, and the report must not quote them until they are reconciled. The first is the GroundLM benchmark: the 0.4% FPR and 0.980 recall for the paper's 270M XLM-R model could not be found in any public source, and the Zenodo 1,393-row benchmark is probably the same data, so it is not independent ([Zenodo](https://zenodo.org/records/20480151)). The team should either cite the source with a DOI or present these as internal numbers. The second is the false-positive rate: the hybrid's "35-39%" in the Hinglish notes and the student's "41.6%" in the current state probably come from different configurations, and this must be stated in the report. The third is the latency arithmetic: a p50 of 1.7 s cannot be reconciled with about 10 tok/s decode and 1-2 s of prefill unless each request generates only a handful of tokens, so the team must confirm the tokens per request. The fourth is the retention figures: 84% for 8da4w in the Llama notes and the 67-81% verifier pass rate in the current state measure different things and should be labelled. The fifth is that the 40-row sample gives an unstable p95, which is effectively the second-largest value, so the 200+ run in rank 6 is necessary.

Other risks are concrete. Donated SMS contain personal data, so consent, redaction and storage rules must be settled before collection, and the research notes found no licence-clean Indian transactional SMS corpus. Chakshu is a DoT channel for suspected fraud communication, not financial fraud, and no public API was found, so the app can only link to it ([Business Standard](https://business-standard.com/industry/news/dot-s-new-chaksu-new-portal-to-allow-citizens-to-report-fraudulent-calls-124030401000_1.html)). The "beat published SOTA" bar that the team sets for itself cannot be checked yet, because the notes offer no published FPR for comparable systems, and the Zenodo LLM-API results publish scores but no FPR or recall. Finally, the weak USB supply can cause undervoltage throttling that shows up as latency spikes on camera, so the official supply is a must-have before filming.

## Conclusion

The novel takeaway is that the team's distinctive asset is not the explainer. It is the verifier-plus-fallback design, which lets the system make a hard guarantee about output safety, and the measured Pi 5 numbers, which few public Indian scam systems publish. Judges are most likely to score the submission on whether it covers the PS3 text and whether it is honest about its own numbers. A report that names the 41.6% false-positive rate, reports the network-IDS cross-dataset drop, and labels in-sample results will score better than one that polishes the explainer while leaving those gaps open.

The second takeaway is about sequencing. Most of the remaining Llama work (constrained decoding, QAT re-export, prefix-KV reuse) has a long payoff horizon and an unverified runner-support question, so it belongs in Phase 2. The Phase 1 window is better spent on deliverables and on the two detection questions, because those decide how the judges read the scope and the measured numbers.
